# Архитектура VoiceFlowWin

## Состав решения

| Проект | Целевая платформа | Назначение |
| --- | --- | --- |
| `VoiceFlowWin.Core` | `net8.0` | Модели, состояния сегментов, обработка текста, координатор, оркестратор диктовки, настройки, словарь, команды, менеджер моделей |
| `VoiceFlowWin.Audio` | `net8.0` | Кольцевой буфер, конвертация формата, VAD, сегментация речи |
| `VoiceFlowWin.Vosk` | `net8.0` | Загрузка моделей и потоковое распознавание |
| `VoiceFlowWin.Whisper` | `net8.0` | Финальное распознавание через whisper.cpp и очередь задач |
| `VoiceFlowWin.Windows` | `net8.0-windows` | Win32: ввод текста, хуки, хоткеи, буфер обмена, фокус, права, WASAPI |
| `VoiceFlowWin.Updater` | `net8.0` | SemVer, манифест, загрузка и проверка пакетов, планировщик проверок |
| `VoiceFlowWin.UpdaterHost` | `net8.0-windows` | Отдельный процесс установки обновления |
| `VoiceFlowWin.App` | `net8.0-windows` | WPF: трей, overlay, настройки, менеджер моделей, внедрение зависимостей |

Границы проведены по одному принципу: **всё, что можно проверить тестом без
Windows, живёт в кроссплатформенных проектах**. Поэтому вся логика, от которой
зависит сохранность пользовательского текста, покрыта тестами, которые
выполняются на каждом PR — в том числе на Linux-агенте.

Ядро не знает о Win32 и о конкретных движках распознавания: оно работает через
интерфейсы `IAudioCaptureService`, `IStreamingRecognizer`, `IFinalRecognizer`,
`ISpeechSegmenter`, `IFinalRecognitionQueue`, `ITextInjectionService`,
`IFocusTracker`, `IInputInterventionMonitor`, `IGlobalHotkeyService`,
`IEscapeStopService`. Реализации подставляются контейнером в `App.xaml.cs`.

## Поток данных

```text
WasapiAudioCaptureService
   │ PCM 16 kHz mono 16 bit (уже сконвертированный)
   ├──────────────► SpeechSegmenter ──► VAD ──► завершённый сегмент
   │                                              │
   └──────────────► StreamingVoskRecognizer       │
                          │ промежуточные          │
                          ▼ гипотезы               ▼
                   StablePrefixProcessor    WhisperTranscriptionQueue
                          │ стабильный текст       │ финальный текст
                          ▼                        ▼
                   HybridTranscriptionCoordinator ◄┘
                          │ план правки
                          ▼
                   TextInjectionService (SendInput / буфер обмена)
```

Vosk и Whisper получают **один и тот же** звук: сегментатор отдаёт тот самый
буфер, который слышал потоковый распознаватель, вместе с pre-roll.

## Ключевые решения

### Приложение правит только собственные символы

Главный риск голосового набора — испортить текст, который пользователь писал
руками. Поэтому у каждого сегмента хранится точная строка `InjectedText` —
то, что приложение реально отправило в окно. Любая правка выражается как
«удалить N собственных текстовых элементов и напечатать хвост», а количество
удаляемых элементов ограничено длиной собственного текста.

Поиск фразы по документу не используется никогда: в поле может оказаться
сколько угодно одинаковых слов, и промах означал бы порчу чужого текста.

### Счёт в текстовых элементах, а не в символах

`Backspace` удаляет текстовый элемент, а не UTF-16 code unit. Emoji — это два
`char`, но одно нажатие; комбинирующие символы дают такое же расхождение.
Ошибка здесь означает съеденную букву пользователя, поэтому все расчёты идут
через `TextElements`.

### Монотонный стабильный префикс

Vosk свободно переписывает последние слова гипотезы: «новый система» на
следующем шаге становится «новую систему». `StablePrefixProcessor` вводит слово
только когда оно повторилось в нескольких гипотезах подряд либо достаточно
долго не менялось, и при этом не входит в последние слова фразы.
Подтверждённый префикс никогда не сокращается — иначе пришлось бы удалять
текст, который пользователь уже видит. Ошибки в подтверждённой части исправляет
Whisper.

### Заморозка сегмента при вмешательстве

`InputInterventionMonitor` следит за клавиатурой (через общий низкоуровневый
хук) и за фокусом с положением каретки (через опрос `GetGUIThreadInfo`). Любой
признак вмешательства переводит сегмент в состояние `Frozen`: автоматическая
замена запрещается навсегда для этой фразы, уже введённый текст остаётся, а
результат Whisper показывается в overlay с кнопками ручного применения.

Собственный ввод отличается от пользовательского по метке в `dwExtraInfo`
структуры `INPUT` и по счётчику подавления, который держит
`SuppressSelfInput()`.

### Один хук на приложение

И push-to-talk, и остановка по `Esc` слушают один экземпляр
`LowLevelKeyboardHook`. Два независимых хука конкурировали бы за одно нажатие и
мешали друг другу его гасить. Хук живёт на отдельном потоке с собственным
циклом сообщений: `WH_KEYBOARD_LL` вызывается в потоке, установившем хук, и
если этот поток занят отрисовкой окна, Windows молча снимет хук по таймауту.

### Два механизма горячей клавиши

`RegisterHotKey` используется для Toggle с модификаторами: система сама даёт
эксклюзивность и сообщает о конфликте. Для push-to-talk и одиночных клавиш
нужен хук — `RegisterHotKey` не сообщает об отпускании клавиши.

Сочетание хранится как virtual key code с модификаторами, а не как символ:
иначе назначенное на русской раскладке сочетание «переезжало» бы на другую
физическую клавишу при переключении языка.

### Сериализация событий

События приходят из потока WASAPI, потока распознавания, очереди Whisper и
потока хука. `DictationController` не обрабатывает их на месте, а складывает в
канал и выполняет строго по одному в единственном фоновом потоке. Это
гарантирует и потокобезопасность состояния сегментов, и порядок: сегмент не
закроется раньше, чем к нему применилась последняя гипотеза.

### Очередь Whisper на одну задачу

Пока Whisper обрабатывает фразу, микрофон продолжает писать следующую. А вот
два одновременных тяжёлых распознавания на слабом CPU превращают задержку в
десятки секунд, поэтому задачи выполняются строго последовательно.

### Энергетический VAD вместо Silero

Детектор речи реализован на RMS и частоте переходов через ноль с адаптивным
уровнем шума и гистерезисом. Это решение без внешних моделей и без ONNX
Runtime: минус сотни мегабайт зависимостей и заметная экономия CPU на каждом
кадре. Интерфейс `IVoiceActivityDetector` вынесен отдельно — Silero VAD можно
подключить позже, не трогая сегментацию. Компромисс описан в
[LIMITATIONS.md](LIMITATIONS.md).

### Безопасность обновлений

Пакет скачивается во временный файл `.download` и переименовывается в `.exe`
только после проверки размера, SHA-256 и (при наличии) подписи. Непроверенный
файл физически не может быть запущен. Имя файла берётся из URL и очищается до
простого имени без разделителей пути, а итоговый путь проверяется на
принадлежность каталогу обновлений.

Токен GitHub в приложении не хранится: манифест и релизы читаются анонимно.

### Выпуск собирается только на Windows

Пакеты `Vosk` и `Whisper.net.Runtime` выбирают native-библиотеки по
операционной системе сборки, а не по целевому RID: `Vosk.targets` явно
проверяет `IsOsPlatform(Windows)`. Кросс-сборка на Linux даёт рабочие
managed-сборки, но кладёт рядом `libvosk.so` вместо `libvosk.dll`. Поэтому
`dotnet publish` и сборка установщика в CI выполняются на `windows-latest`, а
Linux-агент используется только для быстрых тестов.

## Состояния сегмента

```text
Recording ──► Streaming ──► AwaitingFinalization ──► WhisperProcessing ──► Finalized
     │             │                 │                       │
     └─────────────┴─────────────────┴───────────────────────┴──► Frozen | Cancelled | Failed
```

`Frozen`, `Cancelled`, `Failed` и `Finalized` терминальны: результат Whisper к
ним больше не применяется.

## Хранение данных

Всё пользовательское лежит в `%LocalAppData%\VoiceFlowWin`:

```text
settings.json      настройки
dictionary.json    пользовательский словарь
Models\            скачанные модели Vosk и Whisper
Updates\           проверенные пакеты обновлений
Logs\              технический лог без содержимого диктовки
```

Установщик и обновление этот каталог не трогают, поэтому настройки, словарь и
модели переживают переустановку.
